# Sorter

**Assign two human scorers to every project — evenly, and with as few repeated
pairings as the numbers allow.**

Built for research where items are double-scored so inter-rater agreement can be
measured. Works for any two-rater scoring task: it only ever deals in counts and
integer scorer IDs.

- Every project is scored by **two different** people.
- Everyone gets **about the same number** of projects — never more than one apart.
- The **same two people are paired as rarely as possible**.

That last point is the one usually missed, and the most damaging to omit. If
raters are allocated in fixed pairs, a high agreement figure is confounded with
pair identity: two people who share a misreading of the rubric will agree with
each other consistently, and that looks exactly like accuracy. Dispersing
pairings checks each rater against a different partner over and over, so a shared
idiosyncrasy tends to surface as disagreement somewhere.

There is a second script for when someone can no longer finish their work. It
hands their projects to the people who remain **without disturbing anyone else's
list**.

---

## Requirements

Python 3.9 or newer. **That is the whole list.**

No pip install, no virtual environment, no internet. Standard library only —
including the Excel output, which is written directly rather than pulling in a
spreadsheet package. Clone or copy the folder anywhere and run it; the launchers
check everything they need before starting.

## Quick start

| Platform | Assign scorers | Reassign after a dropout |
|---|---|---|
| macOS | double-click **Start Main Assign.command** | **Start Reassign.command** |
| Windows | double-click **Start Main Assign.bat** | **Start Reassign.bat** |
| Linux | `./"Start Main Assign.sh"` | `./"Start Reassign.sh"` |

On Linux, make them executable once: `chmod +x *.sh`

Or run directly:

```bash
python3 assign.py
python3 reassign.py
```

### Assigning

```
How many projects are you going to score?  120
How many people are available to score?    8
```

It shows what it worked out, asks you to confirm, then writes a timestamped
folder under `output/`:

```
output/2026-09-12_143005/
  assignments.csv        the sheet
  assignments.xlsx       the same sheet, as a real Excel workbook
  summary.txt            loads, pairing spread, and a pairing matrix
  run_info.txt           what was asked for and what came out
```

| Project ID | First Scorer | Second Scorer | First Scorer Done | Second Scorer Done |
|---|---|---|---|---|
| 1 | 2 | 7 | | |
| 2 | 3 | 6 | | |
| 3 | 4 | 5 | | |

The two **Done** columns are for marking work as it is completed — `yes`, `y`,
`x`, `done` or `1` all count. They matter only for reassignment; ignore them and
nothing changes.

### Reassigning

```
Which scorer IDs need their projects reassigned? (comma separated):  3,7
```

Only the slots those people held are refilled. Everyone who stays keeps every
project they already had, and anything already marked done stays with whoever
did it — even if that person is the one leaving.

Output goes to a new `..._reassigned` folder. **The original sheet is never
modified.** Alongside the updated sheet you get `changes.csv`:

| Project ID | Slot | Previous Scorer | New Scorer |
|---|---|---|---|
| 2 | First Scorer | 3 | 4 |
| 2 | Second Scorer | 7 | 5 |

You can reassign a reassignment as often as needed, as long as two scorers remain.

## Checking the result

You don't have to take the split on trust. Every run writes `summary.txt` with
each scorer's load, a matrix of how often every pair shares a project, and how
those figures compare with the best mathematically possible:

```
Highest load: 12   Lowest load: 11   Difference: 1
  OK    Evenly split — no scorer carries more than one project above another.

Most times any two scorers share a project: 2
Best achievable for these numbers:          2
  OK    Pairings are as spread out as the numbers allow.
```

## How it works

All possible pairs are generated by the **circle method** — the construction used
to schedule round-robin tournaments — which orders them so consecutive pairs
share nobody. Walking that list, and cycling it when there are more projects than
pairs, achieves both goals at once: pairings repeat only when they mathematically
must, and every full pass is perfectly balanced. A repair pass evens out whatever
a partial pass leaves behind.

With `S` scorers there are `S × (S−1) / 2` possible pairs. With no more projects
than that, **no two scorers are ever paired twice**. Beyond it, each pairing
repeats at most `ceil(projects / possible pairs)` times — the minimum anyone
could achieve.

**Verified, not asserted.** Across 585 combinations of project and scorer counts
(2–40 scorers, 1–1000 projects): workload difference never exceeded one project,
pairing repetition always hit the theoretical minimum, and no project ever
received the same scorer twice. Reassignment was checked over 210 scenarios: no
remaining scorer's allocation was ever disturbed.

`DESIGN.md` has the formal statement, the bounds, and the full verification.

## Options

Both scripts accept arguments, which the launchers pass straight through:

```bash
python3 assign.py --projects 120 --scorers 8 --yes

python3 reassign.py --input output/2026-09-12_143005/assignments.csv \
                    --leaving 3,7 --yes
```

Check an installation without running anything:

```bash
python3 -m sorter.selfcheck
```

## Notes

- Scorer IDs are plain integers, `1` upward. The tool never sees names, so a
  sheet can be shared without carrying identifying information — keep the
  ID-to-person mapping yourself.
- Two scorers is the minimum. With exactly two they both score everything; there
  is no other pairing available, and the tool says so.
- Runs are never overwritten. Each writes a new folder, suffixed if two land in
  the same second.
- Results are deterministic: the same inputs always give the same allocation, so
  a study's assignment is reproducible from its parameters. If your design calls
  for randomisation, shuffle which person holds which ID — that randomises
  without disturbing the balance or pairing properties.
- Closing the terminal window stops the run.
